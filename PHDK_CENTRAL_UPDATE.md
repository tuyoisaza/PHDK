# Centralized PHDK updates

At each authorized PHDK Preflight, compare the locally installed VERSION with a fresh canonical main VERSION. If upstream is newer and managed standards are clean, synchronize manifest-owned standards only, verify the result and reload instructions before continuing. Protect project source, local customizations and uncommitted work. Never downgrade. No background service or dormant-project rollout.

Before invoking the copier, inspect installed source provenance and committed customization/owner-rule differences under PHDK_UPGRADE.md. A clean worktree is not proof that committed owner overrides are absent. The helper detects uncommitted conflicts but cannot establish ownership or preserve unknown committed exceptions by itself; resolve those differences conservatively or report the exact conflict before copying. Do not silently force replacement.

Use the vendored `scripts/phdk_update.py <project> --trigger preflight` for ordinary foreground Preflight; omitting the flag preserves that behavior for existing callers. Use `--trigger upgrade` when invoking the helper for an explicit `PHDK upgrade` or `PHDK upgrade force`. The helper always remains conservative: the flag does not enable force replacement, alter managed blocks, or grant publication authority. The complete command, including ownership checks and any separately authorized force handling, follows [PHDK_UPGRADE.md](PHDK_UPGRADE.md).

After synchronization, follow the **Stack Security Review** in [PHDK_SECURE.md](PHDK_SECURE.md#stack-security-review). Every explicit Upgrade/Force requires the review even when no files change or the installed version is newer. Ordinary Preflight requires it once when it actually adopts a new standards version. Reuse valid evidence within the same command and revalidate affected evidence after a material stack change; do not repeat a portfolio audit at every lifecycle stage.

The updater reports `standards_sync`, previous/adopted/upstream version and upstream SHA separately from `stack_review_required`, `stack_review_coverage` and `stack_security_status`. `MANIFEST_VERIFIED` covers only the manifest copy, not native managed-block verification or application security. A required review is emitted as `PENDING`; security remains `UNVERIFIED` until the agent collects and evaluates the evidence. `NOT_TRIGGERED` means this Preflight adopted no new version, not that the stack is secure. A blocked sync likewise makes no security claim. The helper does not run an advisory scanner, contact a provider, install packages, or perform the review itself.

Keep standards-sync success, review coverage and security findings independent. Finding a project vulnerability does not undo or prevent delivery of safer standards; product remediation and publication retain their existing current-request boundaries. Do not claim vendoring repaired Node, a framework, an image or a deployed service.
