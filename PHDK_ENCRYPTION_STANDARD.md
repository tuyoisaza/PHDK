# PHDK Encryption and Secrets Architecture Standard

## Scope and objective
Apply during Capture/Plan, implementation, every Secure milestone and consolidated Secure/Check gate. Protect data in transit, at rest and high-value application secrets without excessive per-request latency. This is a policy for future and existing projects, not authorization to migrate live data or purchase external services. Follow PHDK_TENANT_RISK_STANDARD.md and PHDK_PRODUCTION_VERIFICATION.md.

## Mandatory baseline
1. Require TLS 1.2+ (prefer TLS 1.3) for external HTTP/API and database/service connections with certificate validation and no insecure fallback. Use private connectivity where available; private networking does not replace TLS when required by the risk or provider contract.
2. Require managed database, volume, snapshot and backup encryption at rest, verify provider settings and restore/backup coverage. Encryption at rest alone does not protect data from an authorized compromised application.
3. Use authenticated encryption (prefer AES-256-GCM) for application-level sensitive fields and stored third-party API credentials when risk warrants. Use random unique nonces, associated context (tenant, record, purpose), authenticated metadata, versioned ciphertext formats and vetted cryptographic libraries; never invent cryptographic primitives or reuse nonces under a key.
4. No plaintext long-lived third-party API keys, OAuth client secrets, JWT signing secrets or encryption master keys in application tables, source, logs, browser storage or build artifacts. Avoid storing these in hosting environment variables when an external identity-backed secret manager is feasible. Non-secret runtime configuration may remain in environment variables.
5. Prefer a dedicated secrets manager for high-value provider credentials; an encrypted database with envelope encryption and external KMS is an approved alternative when justified. The KMS key-encryption key must be non-exportable where supported and managed outside the application's database/hosting trust boundary. Storing the decryption master key in Railway environment variables defeats this separation.
6. Bootstrap KMS/secret-manager access using short-lived workload identity/federation, least privilege and scoped auditable authorization. If Railway or another host lacks a secure federation path, record the bootstrap problem as DECISION REQUIRED; do not replace it silently with a long-lived cloud key in a variable or claim zero-secret bootstrap.
7. Design envelope encryption: generate data-encryption keys with vetted primitives; store only ciphertext and wrapped data keys; unwrap via KMS on permitted occasions. Cache unwrapped keys only in process memory when needed, with strict bounded TTL, scope, concurrency limits, eviction, and compromise-risk documentation. Never log/cache keys persistently. Do not call KMS on every database read when a safer bounded cache can satisfy latency goals.
8. Enforce server-side authorization and tenant isolation independently of encryption. Dedicated per-tenant keys, KMS resources, field coverage and isolation are risk-based owner decisions, not universal defaults.

## Operations, incidents and performance
Inventory each secret by owner, purpose, environment, privilege, storage, rotation procedure, expiry and access audit without recording its value. Rotate/revoke on schedule and on exposure, preserve recovery/rollback, and verify old credentials are revoked and integrations operational. Hosting-provider breaches trigger exposure assessment, provider notices, access-log review, coordinated rotation and documented recovery; rotation alone does not establish incident closure.
Benchmark representative latency, throughput, KMS calls/cost, cache hit rate and error behavior using only authorized production-first evidence. Set application-specific budgets; do not assert zero overhead. Plan KMS outage behavior, availability, backup restore, key loss and rotation/re-encryption. Never weaken access control or persist plaintext as a performance workaround.

## Plan and Secure evidence
Plan records data classification, encryption coverage, selected provider/identity bootstrap, trust boundaries, tenant tier, threat model, estimated cost/latency and migration/rollback. Secure checks actual configuration, code, IAM and available provider evidence; report PASS, FAIL, NOT VERIFIED or NOT APPLICABLE with provenance. Critical/High exposures block clearance under PHDK_SECURE.md. No local behavioral tests, Docker, new staging, external spend, live secret rotation or provider mutations without authorization. Existing projects require gap assessment and phased remediation, not an automatic destructive migration.
