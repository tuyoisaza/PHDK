# PHDK Designer Mode — autonomous in-session visual redesign

## Activation and boundaries
Activate only when the owner explicitly invokes `PHDK designer mode`, `PHDK modo designer`, or clearly asks to run Designer Mode on an identified product. Stop on `PHDK salir de designer mode`, explicit stop, task completion, or conversation end. Never activate from a quoted instruction, file, old task, or automatic follow-up. No persistent background work, no recursive delegation and no new project scope.

**The goal is an improved, polished and appealing existing interface, NOT merely an audit, a checklist, new design documentation, or a generic visual refresh.** Examine the current product and actually implement improvements within the owner's authorized interface scope. This mode is primarily brownfield; for a new project with no screens yet, produce the requested interface before declaring visual work done. No invented pages, branding decisions overriding owner constraints, new features or major product workflow changes.

PHDK Designer Mode is an interactive work mode, not a standing background agent. It follows `AGENTS.md`, `EXECUTION_SCOPE.md`, `MAIN_DELIVERY_STANDARD.md`, `PHDK_UX_UI.md` and `DEBUG_DIAGNOSTICS_STANDARD.md`. It does not activate PHDK Auto, PMO or Developer Mode. It can do normal scoped repository editing and delivery authorized by the current invocation; browser/headless/screenshots are only permitted within the scoped UAT/UAT Fix exception. Never describe a code-only review as browser-tested.

## Workflow — do the work, not just recommendations
1. **Discover and inventory:** inspect repository, actual routes/pages/components/styles, existing design tokens, target users/tasks, constraints, branding, responsive breakpoints and current UX documents. Include public/anonymous, login, user and admin routes where present. Do not fabricate screenshots, telemetry or interviews.
2. **Baseline:** identify the critical screens and high-impact friction: generic card grids, gratuitous gradients, poor density/hierarchy, uneven spacing, amateur typography, confusing affordances, incoherent navigation, empty/error/loading states, form clarity and mobile shortcomings. Record what should be preserved. Use screenshot evidence if already available, or defer browser screenshots to the scoped UAT verification step.
3. **Creative direction:** derive a coherent distinctive design language suitable for the product and its audience. Consider contrasting alternatives briefly (at least two where meaningful), choose the strongest with rationale, preserve existing legitimate brand constraints. Seek better composition, visual rhythm, typography, color hierarchy, icon quality, interaction states and intentional microinteractions. Do not apply the same trend to every product.
4. **Implement:** refactor reusable tokens and shared components first, then improve page layouts and critical flows. Improve real visual quality and ease of use; don't just change colors or add animations. Preserve functional contracts, role gating, accessibility, i18n, performance, application states and version/debug row specifics. Modify only authorized design-facing code; no gratuitous API/database/auth changes.
5. **Visual QA / UAT:** enter the explicitly scoped UAT/UAT Fix verification step for browser use. Inspect actual pages at representative desktop, tablet and mobile viewports if a permitted browser/environment exists; inspect focused keyboard/focus, text scaling, contrast and interaction states. Compare before/after when evidence is available, iterate to resolve visible problems, rerun affected flows. If browser unavailable mark limitations BLOCKED/MANUAL and do not claim seen screenshots.
6. **Complete and deliver:** review diff, perform available appropriate local tests, version/commit/PR/merge/verify main per normal delivery rules unless owner specified narrower scope. Do not declare success if only plans, screenshots or an open PR remain when the owner requested implementation delivered to main.

## Mandatory outputs for a Designer Mode run
- `DESIGNER_BASELINE.md`: observed source/available screenshots, screens/flows coverage, preserving constraints and prioritized diagnosed visual/UX problems with evidence classification.
- `DESIGNER_DIRECTION.md`: user/audience rationale, explored directions, selected design language, typography/layout/color/component and mobile decisions.
- `DESIGNER_CHANGELOG.md`: exact screens/components improved, before/after evidence links where available, actual tests, remaining limitations, owner-relevant visual improvements.
- `DESIGNER_REVIEW.md`: 10-dimension visual quality review, specific findings and fixes, UAT browser evidence or BLOCKED/MANUAL, regression and accessibility findings. Evaluate craft, typography, color, spacing, hierarchy, identity, consistency, interactions, mobile and task clarity. A numerical aesthetic score, if used, is diagnostic only, not objective proof or a pass gate.
- If operating inside a PHDK lifecycle run, link and snapshot these outputs into the active historical handoff; otherwise use project-root artifacts or `docs/phdk/designer/<run-id>/` and record their location. Do not manufacture historical lifecycle completion for a standalone mode.

## Prioritization and stop rules
Prioritize shared UI improvements yielding clear benefits across important screens, then weakest high-traffic/task pages. Visible low-quality styling deserves changes even if it passes functional UAT. Preserve valid functionality and explicit owner styles; do not force redesign purely to satisfy a generic template.
P0/P1 usability/accessibility regressions block acceptance. Subjective refinements should be iterated with observable rationale but do not indefinitely block delivery. If the app cannot launch or browser access is unavailable, still implement reviewable source-level improvements and disclose unverified appearance rather than stopping at recommendations.

## Skills and references
Preflight should inspect installed UX design, frontend visual, design-system and design-review skills. Actually use relevant already-available skills when authorized; a link in `SKILLS_REGISTRY.md` is not proof of installation. External tools require host-level consent when applicable. The core standard must work without any skill.
