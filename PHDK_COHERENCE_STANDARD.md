# PHDK Coherence Standard

## Mandatory canonical release review
Before publishing PHDK, inventory applicable standards, manifest files, scripts, agent entrypoints and changed dependencies. Review contradictory requirements involving Preflight, AUTO/PMO, delegation, UAT/browser permissions, security scope, delivery, and completion evidence. Record exact conflicting files and smallest fixes. Documentation never substitutes for implementation and executed test evidence.

## Preflight policy
Run universal Preflight ONCE at each PHDK command entry. For stages inside Auto/PMO, validate upstream handoffs and check newly relevant capabilities without repeating full Preflight. Repeat the universal audit only if installation, VERSION, manifest, or managed instructions have changed or failed integrity checks.

Apply [Stack Security Review](PHDK_SECURE.md#stack-security-review) on explicit Upgrade/Force, including a no-op, and when foreground Preflight actually adopts a new standards version. Reuse unchanged evidence within the active command; refreshing a capability or re-entering a stage alone does not repeat the full stack review. Report standards synchronization, review coverage and security findings independently.

## Release gates
- VERSION, README and newest CHANGELOG release must match and all three files must be included in the vendoring manifest so downstream coherence checks receive the same release inputs.
- Every vendoring manifest source must exist, with unique safe source/destination paths.
- Run the static coherence checker and applicable existing repository checks when an execution environment is available. A static pass does not certify semantic coherence or behavior.
- Review full outgoing diff for conflicting instructions and non-vendored new dependencies.
- Review [hook decision routing](PHDK_HOOK_COMPATIBILITY.md#decision-procedure) for ambiguous or conflicting build/packaging/hook commands before executing them, declaring them BLOCKED or asking a related question. Static guards require the trigger in the active agent/Auto entrypoints and installed native managed block, the procedure and six decision-scenario rows, and correctly vendored hook/verification dependencies. Review the scenarios for permitted compiler execution, compiled-application load checks, scoped PHDK repair, owner/unknown provenance and pre-push order. These source checks do not prove script safety, agent compliance, runtime coverage or downstream adoption.
- Review Stack Security Review routing across Upgrade, Preflight, Plan, Check, delivery and managed entrypoints. Preserve the supported Active LTS / Maintenance LTS selection rule, current official advisory evidence, declared/resolved/build/deployed distinctions and independent `STANDARDS_SYNC`, `STACK_REVIEW_COVERAGE` and `STACK_SECURITY_STATUS` outcomes. Synchronizing safer standards must not certify or silently remediate the product. The static checker validates contract markers, routing and manifest dependencies and rejects known obsolete sync-only, Node 20 minimum and local-test clauses; it does not look up advisories, establish exploitability or verify a deployed runtime.
- Run the checker against both the canonical checkout and the vendored `phdk-standards/` layout when distributing a change. Canonical existence checks use manifest sources; installed-layout existence checks use mapped destinations, including renamed uppercase files. Validate every source/destination path and byte-compare the distributed manifest separately; a static policy pass alone does not prove a faithful sync.
- Review [phase-transition reconciliation](MAIN_DELIVERY_STANDARD.md#phase-transition-reconciliation) across Plan, task records, delivery and managed entrypoints. Check restriction provenance, lifetime, closure/supersession evidence and preserved history; keep owner authorization, technical permission, cost authorization and UAT authorization separate. Static guards require the active contract sections, record fields, routing references and vendored dependencies. Their presence neither grants permission nor proves that an executor accepted a transition; validate actual operation evidence separately.
- Reconcile explicit-only UAT throughout instruction bodies, lifecycle sequences, completion examples and managed installation blocks. Auto/Force must leave UAT Prep/UAT/Fix `DEFERRED — OWNER OPT-IN`, report `UAT NOT RUN` separately from development, and never require acceptance to finish delivery. Verify that explicit `PHDK uat` includes necessary Prep, standalone `PHDK uat prep` does not initiate acceptance, and Fix requires its explicit invocation or authorization within an active explicitly initiated UAT. A precedence header does not excuse contradictory body text.
- The static checker rejects known legacy automatic-UAT clauses, affirmative local-runtime test directives, non-deferred Auto acceptance rows and missing managed authorization markers. Its local-runtime guards target the specific obsolete isolated-suite/unit/in-process instructions, not generic test mentions, prohibitions or decision scenarios. These bounded source checks do not prove semantic completeness, runtime behavior, user authorization or downstream adoption; retain full diff review. Archived changelogs and evidence reports are not current instruction sources.
- Reconcile PR checks, reviews, target main SHA, version and commit evidence after merge.
- Do not claim COMPLETE for untested behavior, open required PRs, or unverified remote main.

- Review [post-merge workspace closeout](PHDK_GIT_WORKSPACE_CLOSEOUT.md) routing through Auto, PMO, native agent/skill entrypoints, lifecycle and delivery. Verify both the distributable standard and `scripts/phdk_git_closeout.py` are in the manifest, that local main is updated only by safe fast-forward, and that branch/worktree cleanup preserves dirty, exclusive and unknown ignored data. The helper's presence never proves a local cleanup actually ran; require milestone-specific evidence and explicit remote-only dispositions.

## Audit report
Use PHDK_COHERENCE_REPORT.md with baseline SHA, timestamp, scope and coverage; categorized findings (CONFLICT, GAP, RISK, VERIFIED, UNVERIFIED, N/A), severity, evidence, owners, remediation and exact next action. Distinguish sampled checks from exhaustive audit. A new conversation may run a fresh review on request; no passive background monitoring or inferred authorization to change unrelated repositories.
