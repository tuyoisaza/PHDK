# Synthetic identities for UAT

Use this contract for authenticated products in explicit `PHDK uat prep`, necessary Prep within explicit `PHDK uat`, and authorized UAT Fix. Prep creates and verifies the run's accounts and relationships through the product's existing trust boundary. At UAT, the normal entry point is one authenticated elevated actor using the product's **Test as / Ver como** control. Apply [JWT_STANDARD.md](JWT_STANDARD.md) to the actual session technology and [PHDK_UAT_PREP.md](PHDK_UAT_PREP.md) for phase permissions. A public-only product records why identities are inapplicable.

## Who exists in a run

Inspect the product's actual roles, memberships, area rules and paths for assignment. Record one active, distinct synthetic subject for each applicable **tenant × role** cell in `UAT_ROLE_MATRIX.md`. Cover each area where leadership or routing is part of a story. Add a second same-role subject when a peer handoff or ownership denial needs one. Mark genuinely inapplicable cells with a reason. A required account that could not be created is BLOCKED. Anonymous is a signed-out case. Add suspended/pending subjects separately when those states exist.

| Product model | Company Co reference | Evidence to obtain |
|---|---|---|
| Multi-tenant | Company Co is the platform operator. Its synthetic super admin can select authorized fixtures. Café Bruma and Café Nube Andina are independent synthetic tenants for this scenario. Each gets its own admin and every applicable role. Areas such as Servicio al cliente sit inside a café. | The Bruma lead assigns a run-owned request to the Bruma member. The member sees and acts on that same request. The Nube admin is denied direct access to its ID. An attempted cross-café assignment leaves the record and assignee unchanged. |
| Single-tenant | Company Co is one organization. Its actual admin is the highest actor. Its supported leads and members work in the same organization and retain area and ownership boundaries. | A lead assigns work, the intended member receives it, and an ordinary member is denied an administrative action. No second organization or platform super admin is introduced. |

Use the [fictional topology](COMPANY_CO_UAT_IDENTITIES.json) as a starting roster. Map persona and role keys to the product's actual permission IDs. A department becomes a tenant only if the product itself defines it as a separate isolation boundary. External customers and suppliers get accounts only where the product gives them access. Keep the master Company Co employee and customer records as references.

## Deterministic identifiers and credential custody

The default login address is `uat-{project}-{run}-{scope}-{role}-{slot}@companyco.example.test`. For example, `uat-pos-r7k2-bruma-member-01@companyco.example.test` identifies the first Bruma member in one run. Allocate a fresh opaque run ID and persist it in the run manifest. Use the same project, run, scope, role and slot on a retry. Parallel or subsequent runs use distinct IDs. Use short lowercase alphanumeric keys for project and run, short lowercase slugs for scope and role, and a unique slot such as 01 per scope/role. Validate uniqueness under the provider's normalization and length limits. An address is a lookup hint. Ownership requires the recorded project/run markers and provider subject ID.

Use these reserved addresses with invitations and delivery suppressed. The live contact aliases in the historical Company Co staff table are for demo content. If a provider rejects the reserved domain or requires mailbox verification, use a preauthorized, isolated test inbox or sink and a supported verification flow with the same ownership scheme. Record the approved alias mapping in the project adapter and read back the provider-issued subject. Never assert mailbox possession or set a verification flag by hand. Record a per-account blocker if safe provisioning is unavailable.

Most switched personas need no password in the runner. If the provider requires a credential, generate a separate, cryptographically random provider-compatible secret for each account. Prefer at least 20 random characters when supported. Keep only an opaque reference to the run-scoped secret facility in the manifest; retrieve it there on a retry. Rotate through an authorized reset if needed, then revoke or delete it at cleanup. Never derive passwords from aliases, a numeric sequence or a shared literal. Honor provider policies. For an isolated site before launch, apply the [pre-live MFA and JWT procedure](JWT_STANDARD.md#pre-live-synthetic-mfa-and-jwt-testing) before classifying a missing human second factor as a blocker.

## Prepare, apply and verify

1. Build the desired matrix and linked work items in the existing `UAT_AUTH_PLAN.md` and `UAT_FIXTURE_MANIFEST.md`. A project can render the bundled example offline with the command below. For real Prep, map an adapted catalog to the discovered roles using `--catalog PATH`. The output represents **planned** identities only.

   ```sh
   python phdk-standards/scripts/phdk_uat_identity_plan.py --project pos --run r7k2 --mode multi
   ```

2. During authorized Prep, reuse or implement the project's idempotent provisioner against its supported admin API, provider SDK or seeder. Identify who can create the first fixture before attempting a login. Reuse an authorized provisioning principal, an existing supported owner-enrollment path, or a deployed first-party seeder with narrowly scoped authority. That provisioner creates or reconciles the synthetic elevated actor first; never promote an arbitrary new signup. If no authorized creator exists, report that specific missing capability. Record the project's exact apply, verify and cleanup commands or supported operations, the authorized caller and the deployed target. Reconcile in dependency order: scopes, subjects, application users, memberships and area relationships, then owned records and assignments. Link the application user to the provider's immutable subject ID. Reuse a matching resource only after proving run ownership. A same-email collision with a different or unknown owner blocks that row before any mutation. Handle partial failures and retries at each step.
3. Read back subject, application ID, tenant membership, role, area, relationship and current state. Record the planned key, actual IDs, created/reused/blocked result, evidence and expiry. Reconcile again for the same run and verify that IDs and relationship counts remain stable. A target can be provisioned and ready for Test as on the strength of trusted subject, membership and capability readbacks without signing in as that target. Record the elevated actor’s session readiness separately. A missing provider link or grant leaves the affected cell unverified. Report individual blockers and continue independent cells.
4. Before writes, ensure synthetic data and side effects are isolated. During a continuous authorized Prep-to-UAT handoff, retain only the verified, expiring fixtures still needed for that run. Roll back failed cells without removing valid dependencies of other runnable cases. At the end of standalone Prep, at final UAT closeout or on interruption, revoke sessions and run-owned grants. Remove dependent assignments and records before identities and scopes. Verify revocation and cleanup against the ownership manifest and record any residual IDs for safe cleanup. Never delete resources belonging to another run or real tenant.

## Enter once and test as the selected person

Authenticate the run-owned platform super admin (multi-tenant) or application admin (single-tenant) through the existing provider. Prove its actual authority. If the product legitimately has no elevated test actor, map the supported direct access for its actual roles and document the reason. For elevated sessions, bound UAT operations to the run's fixtures. If those boundaries cannot be enforced, mark the affected work BLOCKED. Standalone Prep verifies permitted non-browser readiness only. The following product journey belongs to explicit UAT.

1. From the normal admin UI select the synthetic tenant and **specific user**. The server authorizes the original actor, the target and its membership, and issues an expiring effective context with only that user's permissions. Keep authenticating actor and effective subject distinct in the audit, including tenant, reason, run, start, end and outcome. Cookie sessions can implement the same contract. A JWT deployment that supports delegated tokens may use the effective user in `sub` and the original actor in `act.sub`.
2. Verify the visible role/tenant banner, a trusted identity readback, business actions and a forbidden API action from the reduced context. The user's requests must never inherit elevated privileges. Use sequential switches or separate isolated contexts for a handoff. Return to the original admin through the authorized server path, invalidate the switched context, then select the receiving user and verify the same item by ID. Verify expiry, revocation and denial of foreign tenants, unowned subjects and unauthorized switch attempts.
3. Use direct sign-in only for a traced authentication case (for example SSO/MFA, login, logout, suspension), or a documented fallback where the product legitimately lacks a switch and allows ordinary synthetic sign-in. If a required switch is broken, record its FAIL once confirmed. An independent login may exercise unaffected business cases, but cannot clear that defect. Report `SWITCHED` and `DIRECT` evidence separately in `UAT_ACCESS_REPORT.md`. Bootstrap, a working switch, a successful login and a business workflow each require their own evidence.

## Basis for the convention

The account hierarchy, address format and café roster are PHDK decisions. These sources inform the implementation.

- A provisioning client can correlate its own durable key with an ID issued by the provider. Use the same distinction with the project's supported API. [SCIM, RFC 7643 §3.1](https://www.rfc-editor.org/rfc/rfc7643.html#section-3.1)
- Delegated JWTs can identify both the effective user and the actor. [OAuth 2.0 Token Exchange, RFC 8693 §4.1](https://www.rfc-editor.org/rfc/rfc8693.html#section-4.1)
- The `.test` suffix is reserved for testing. Suppressing outbound delivery is a separate application/provider control. [Reserved DNS Names, RFC 2606 §2](https://www.rfc-editor.org/rfc/rfc2606.html#section-2)
- Assigned passwords are generated randomly and verifiers screen common or compromised values. [NIST SP 800-63B-4 §3.1.1](https://pages.nist.gov/800-63-4/sp800-63b.html#passwordver)
- Tenant context and access to a specific resource require trusted server-side validation. [OWASP Multi-Tenant Security Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Multi_Tenant_Security_Cheat_Sheet.html)
