# PHDK Secure Standard — v2.63.0

## Contract
`PHDK secure` is an explicit standalone security audit-and-authorized-remediation command. In `PHDK auto` and `PHDK auto force`, Secure is mandatory **development work**, not UAT or UAT Prep. Hybrid operation means lightweight security checks at each completed value milestone and a consolidated security gate after integration and before final Check/delivery. Security findings may require reopening implementation. Never interpret Secure as permission for UAT, penetration testing, paid scanning, external provider mutations, local behavioral tests, Docker, new environments or bypassing controls.

## Milestone checks
For each completed value milestone inspect changed source/configuration and relevant threat boundaries: secrets, dependencies, authentication/session management, server-side authorization and least privilege, tenant isolation across data/storage/jobs/exports/AI, encryption and TLS configuration, input validation and injection, SSRF/XSS/CSRF, rate limiting, logging/PII, backup exposure, supply chain and GitHub/Railway configuration. Run permitted static checks only, preserve existing independent security gates, and document applicability and evidence. Do not claim behavioral assurance from source inspection.

## Consolidated gate
After integration, assess OWASP Top 10 and relevant ASVS controls using a risk-based threat model; reconcile with `PHDK_TENANT_RISK_STANDARD.md`, `PHDK_PRODUCTION_VERIFICATION.md`, current owner decisions and actual hosting architecture. Record each finding with severity, affected asset/tenant boundary, reproducible static evidence, remediation, verification status and residual risk. Fix authorized source/config defects, repeat permitted static checks, and document unverified runtime controls for later explicitly authorized UAT. No fabricated passing tests or acceptance evidence.

## Release decisions
Critical/High confirmed security vulnerabilities block Secure clearance and final delivery until fixed or subject to an explicit, documented owner risk decision consistent with non-waivable host/security controls. An owner waiver cannot bypass technical enforcement or assert a vulnerability is resolved. Unknown/unverified is not PASS: classify its risk and report limits; absent UAT is not itself a Secure failure. Medium/Low findings require documented prioritization and ownership. Do not request routine approval in Auto Force; sensitive architecture, spending and risk acceptance still require owner authority.

## Outputs
At each milestone, record a concise security delta in the milestone handoff. For the consolidated gate, create `docs/phdk/lifecycle/<run-id>/68-secure/HANDOFF.md` and `SECURITY_REPORT.md` with scope, controls matrix, findings, remediation commits, static verification, residual risk, release decision and explicit `RUNTIME SECURITY VALIDATION NOT RUN` where applicable. Record stage in lifecycle status. Standalone Secure audits current state and fixes only within the owner's authorization; read-only invocation must not mutate code.

## Precedence and integration
Secure runs after implementation/integration, before final Check and delivery; it never enters stages 45/50/60. This standard supplements existing tenant, production-verification, Check, delivery, Auto and milestone rules. Existing owner/host controls take precedence. Load this file only at the relevant security stage or milestone rather than in every context.

## Mandatory Node.js runtime and npm supply-chain profile
For every new Node.js project, Plan MUST select the latest security-patched **Active LTS** line compatible with the entire chosen framework, package manager, native addons, database drivers, build tooling and hosting platform. Do not select Current solely because its version number is higher. Verify the actual current Node.js release/security schedule from official sources at planning time; never hard-code a supposedly latest patch release in this standard. Pin the selected major/runtime in package `engines`, package-manager configuration and deployment configuration where supported; record exact resolved production version and support/EOL dates. Do not claim Railway compatibility without inspecting the actual builder/image and deployed runtime. If no Active LTS is compatible, document the incompatibility, recommend a supported stack change, and escalate an explicit risk decision; do not silently select an EOL runtime.

For all Node.js projects (including existing projects), Secure MUST audit the runtime and supply chain at each relevant milestone and at the consolidated gate: verify Node.js security-patch level, supported release line, framework/driver/native-addon compatibility, lockfile integrity and reproducible `npm ci` (or equivalent), transitive dependency advisories, suspicious package releases/maintainer changes, lifecycle/install scripts, secret exposure, npm publisher MFA and provenance/trusted publishing where applicable. Prefer an evidence-backed dependency cooldown for newly published versions, with documented exceptions for urgent security fixes. Do not blanket-disable install scripts if legitimate native builds require them; isolate and explicitly allowlist necessary scripts. Use static inspections and authorized existing provider metadata under PHDK production-first policy; no new local behavioral tests, staging or paid scanners. Treat compromised packages or exposed credentials as incidents requiring containment, credential rotation through authorized channels and documented remediation. Record confirmed issues separately from unverified deployment/runtime claims.

## Superadmin first-use enrollment and recovery
For every stateful administered product, initial superadmin enrollment MUST be explicitly owner-controlled. Never ship a default password, shared superadmin credential, hardcoded email with implicit privilege, publicly reusable bootstrap token or automatic admin account accessible before verification. Establish the designated recovery email during setup, verify mailbox control, and require strong MFA (prefer phishing-resistant passkeys/security keys). The recovery email is a notification/recovery channel, not sufficient authorization by itself.

Generate a cryptographically random, short-lived, single-use enrollment invitation, bound to the intended administrator identity and installation, stored only as a verifier/hash where feasible; expire and invalidate it atomically on use. Enrollment must not grant persistent privilege until required identity verification and MFA setup are complete. Do not log or expose tokens in URLs, telemetry or referrers. Rate-limit and audit enrollment/recovery attempts.

Password loss: use generic anti-enumeration responses, a short-lived single-use reset challenge to the preverified recovery channel plus an independent factor or recovery code, then revoke existing sessions and notify the administrator. For MFA/device loss, issue individually single-use high-entropy recovery codes at enrollment, show them once, store only salted hashes, and instruct offline storage. Email-only reset must never bypass the required second factor for privileged accounts. Rotate recovery codes after use/recovery.

If all factors and mailbox access are lost, provide a separately authorized break-glass process requiring verified organizational ownership and independently audited dual control where feasible; no hidden backdoor or direct unaudited database privilege update. Recovery contact changes require recent strong reauthentication, out-of-band notification and a delay or approval for high-risk changes. Support multiple individually accountable admins where appropriate, with least privilege.

Plan must specify owner identity, recovery-contact custody, bootstrap delivery, MFA, expiry, emergency recovery, audit and operational handoff. Secure checks the implementation and records evidence; UAT runtime journeys remain explicit-only under the existing PHDK policy. Never print live recovery codes, reset links or passwords in reports.
