## v2.62.0 — Explicit-only UAT authorization (overrides legacy automatic-stage wording)

**Binding rule:** `PHDK auto` and `PHDK auto force` MUST NOT invoke, enter, provision, seed, or run UAT Prep (45), UAT (50), or UAT Fix (60), even after milestones, deployment, Check, or a failed prior UAT. Neither FORCE nor a generic full-lifecycle instruction grants UAT authorization. These stages are **DEFERRED — OWNER OPT-IN**, not BLOCKED, FAILED, or a completion prerequisite. This rule takes precedence over any older automatic UAT transitions in this file.

Auto/Force must implement **all authorized milestones first**, perform permitted static checks and integration review, version/commit/push/PR/merge each completed value milestone, finish applicable SEO/AEO and Check/remediation without invoking acceptance tests, deploy through the existing authorized production route, verify remote main and deployment with available non-UAT evidence, and report truthful **DEVELOPMENT COMPLETE / PARTIALLY DELIVERED / BLOCKED** separately from **UAT NOT RUN**. A deployment that cannot be verified must be reported as unverified, not complete. Preserve user stories, acceptance criteria and milestone-to-story mapping as *documentation only*; no synthetic accounts, fixtures, browser journeys, runtime acceptance, or UAT spending in Auto. Do not execute local behavioral tests, Docker, or unauthorized external services.

At the end, offer `PHDK uat` as an optional **future explicit command**, without waiting for an answer as a delivery gate. Only a fresh, explicit owner invocation of `PHDK uat` authorizes UAT and its necessary Prep prerequisite, subject to normal access, safety and spending controls. Standalone `PHDK uat prep` prepares identities only when explicitly requested; it does not authorize running UAT. `PHDK uat fix` requires explicit invocation or authorization within an active explicitly initiated UAT. Prior UAT failures never reopen the completed development goal or prevent subsequent independent development.

# PHDK UAT Prep — Synthetic Identity Readiness

## Command, position and authority

**Command:** `PHDK uat prep`, case-insensitive after whitespace trim; stage 45 is only entered after explicit `PHDK uat` or explicit `PHDK uat prep`; never automatically within Auto. This is an **implementation and provisioning** command, not a planning-only audit. A request to define this command does not activate it in another product. It does not activate Auto, UAT, background work or any browser exception.

On a standalone invocation, complete permitted in-scope application edits, non-browser readiness verification, versioned branch/PR/merge and remote verification under `MAIN_DELIVERY_STANDARD.md`, then stop without launching UAT. When Prep is a prerequisite of an explicit `PHDK uat` run, deliver any source changes through the same authorized route and verify the revised deployed candidate before acceptance. Auto and Auto Force never execute stage 45; they report it **DEFERRED — OWNER OPT-IN** alongside **UAT NOT RUN**.

Read `PHDK_PREFLIGHT.md`, `EXECUTION_SCOPE.md`, `JWT_STANDARD.md`, `UAT_JOURNEY_STANDARD.md`, `USE_COMPANY_CO_INFO_FOR_DEMOS.md` and `ADMIN_CONSOLE_STANDARD.md`. Preserve the existing app's actual auth provider, roles and tenant boundaries. A Company Co employee or role label alone never authenticates an account. JWT is optional; do not impose JWT on an OAuth/cookie/session app.

## Required implementation sequence

1. **Inspect and pin:** project goal and requirements, exact deployed candidate/revision, source-backed auth/session/provider flows, membership/RBAC, tenancy, existing seeders and `Ver como` feature. Verify current Integration evidence when available. Confirm the existing production application/database and explicit Prep or UAT authorization under `PHDK_PRODUCTION_VERIFICATION.md`; a URL or `TEST_MODE` flag alone proves neither permission nor safe synthetic isolation. Do not create a local/staging environment or test database.
2. **Design the minimum role fixture:** inventory anonymous, inactive/suspended, real ordinary/manager/customer/supplier profiles, and correct platform authority (**multi tenant = platform `super_admin` and tenant admins; single tenant = application `admin`, no redundant super-admin**). Map a *representative subset* of Company Co's 200 fictional employees and commercial profiles to stable synthetic IDs. For multi-tenant create two **synthetic** tenants when isolated testing needs cross-tenant denial. No unnecessary mass-account creation.
3. **Build or repair repeatable identity provisioning:** implement checked-in idempotent seed/upsert scripts or use the existing approved application/provider administration mechanism, without changing provider configuration. Bind provider `sub`, active status, tenant membership, permissions, domain records and fixture owner/run ID. Prove permitted repeated runs do not duplicate records or escalate permissions. **Actually provision** the minimal authorized run-owned synthetic accounts on the deployed candidate when safe access exists; record exact missing external steps instead of claiming they exist. Deliver necessary source changes before executing them; preserve real-data and migration restrictions.
4. **Build/reuse authenticated session bootstrap:** use real supported application/provider sessions for the run-owned synthetic identities and preserve ordinary authentication, MFA and server-side authorization. In-scope source support may connect the existing trusted mechanism to exact allowlisted fixture/run IDs; it must not add a new trusted issuer, public bypass route or arbitrary impersonation capability. Enforce caller authority, current role/tenant membership, expiry, audit and revocation. If no supported safe mechanism exists, record the precise blocker. No public "login as superadmin" endpoint, default password, MFA disablement, hand-minted bearer string or production auth bypass.
5. **Support role test:** prepare independent synthetic identities/sessions for each applicable user and an elevated actor. If the application already requires `Ver como / Test as`, implement/fix the authenticated server-enforced restricted-role switch (actor/target/tenant/expiry/audit, visible banner and return) **within authorized feature scope**. Do not confuse test bootstrap with product impersonation. Escalation, cross-tenant access and real-user impersonation are prohibited.
6. **Isolate and prove:** prevent real email, payment and third-party side effects using already supported safe routing; exclude real people/data and new paid dependencies, and establish cleanup/revocation/TTL before writes. Run only permitted non-browser provisioning/readiness checks on the exact deployed candidate for idempotency, resolved identity, role/tenant limits, expiry and cleanup. Record full acceptance journeys and JWT negative cases for the explicitly authorized UAT phase. Local work remains source review/static checks/builds; no local unit/in-process tests, databases or Docker. Record real results; no invented API/browser/SSO evidence.
7. **Handoff:** write the four canonical artifacts below and record blockers individually. Continue into acceptance only when Prep belongs to an active explicit `PHDK uat` run; standalone `PHDK uat prep` ends after readiness and cleanup, offering UAT as a future command. A missing buildable seeder or safe session integration is an implementation issue within Prep's authorized scope, **not** a reason to ask for the owner's personal passwords or defer routine work until UAT Fix.

## Mandatory app artifacts and proof

| Artifact | Required evidence |
| --- | --- |
| `UAT_AUTH_PLAN.md` | environment/revision, existing provider + chosen safe bootstrap, trust boundary/secret references (never values), exact role/tenant access plan, revocation and cleanup |
| `UAT_ROLE_MATRIX.md` | source-backed personas, fixture IDs, actual allowed/denied permissions, tenant boundaries, elevated and anonymous/inactive identities, coverage |
| `UAT_FIXTURE_MANIFEST.md` | seed source/command, deterministic Company Co subset, per-role account/subject/tenant/status (no passwords/tokens), provisioning result, idempotency and rollback/cleanup |
| `UAT_PREP_REPORT.md` | candidate + environment, source changes, actual seed/provider actions and permitted non-browser readiness results, per-role `READY`/`BLOCKED`/`UNVERIFIED`/`N/A`, run-owned data isolation and cleanup evidence, exact next action |

Inside an explicitly initiated UAT lifecycle, create immutable sanitized snapshots plus `docs/phdk/lifecycle/<run-id>/45-uat-prep/HANDOFF.md`. A standalone Prep invocation does not fabricate a lifecycle run, and Auto does not require or create a Prep execution handoff.

**READY:** all required run-owned synthetic accounts are provably provisioned for the authorized run, trusted session issuance and permitted readiness checks pass, and isolation/expiry/cleanup controls are evidenced. Never mark an externally missing role READY. Standalone Prep must complete and verify cleanup at closeout; its historical readiness report does not authorize retaining sessions or skipping fresh provisioning/access checks in a later UAT run. **PARTIAL/BLOCKED:** missing provider permission, safe target, account, test-as feature, needed runtime proof or owner policy decision; continue all independent permitted work and enumerate impacted roles/cases. **N/A:** truly no authenticated user surface with source evidence. **REUSED:** revalidate source, deployed revision, role scope, state expiry, readiness and cleanup; do not reuse a stale assertion.

## UAT transition, source changes and browser boundary

Explicit UAT order only: **current Integration/deployment evidence → 45 UAT Prep → 50 UAT → separately authorized 60 UAT Fix when needed**. Auto/Force never enter stages 45–60. Prep **must not** launch Playwright, browser/headless tests, screenshots, OAuth login pages or full acceptance journeys. The browser exception only starts on entry to explicitly authorized UAT/UAT Fix under `UAT_BROWSER_READINESS_STANDARD.md`. At UAT entry separately verify real connected browser availability and safe target; a complete Prep handoff does not prove browser access.

When Prep alters application code/schema after the prior Integration Review, repeat affected static/integration review, deliver the source change, verify the deployed revision and **refresh the current `INTEGRATION_REPORT.md` to identify the changed candidate**, preserving earlier immutable history. Perform any required non-browser readiness calls only on that authorized deployed revision. UAT must inspect this reconciled candidate and exact Prep outputs before attempting logged-in stories. Explicitly authorized UAT Fix may repair a newly discovered Prep defect and rerun its permitted readiness checks; UAT Fix is not the normal initial provisioning phase.

**Never** modify real users/roles, grant arbitrary privileges, change live identity-provider/hosting settings, access real customer data, send unsolicited invitations, purchase services, request arbitrary spending caps or ask humans to paste secrets. Run-owned synthetic elevated identities are permitted only through existing legitimate authorization under `PHDK_PRODUCTION_VERIFICATION.md`, with exact ownership, scope, audit and revocation. If safe access or a necessary external authorization is missing, identify that prerequisite and mark only dependent work BLOCKED. Do not claim success for unrun checks or accounts not actually created.

**Final status contract:** report `Prep READY/PARTIAL/BLOCKED/N/A`, actual source-delivery state, verified evidence paths, cleanup and outstanding role blockers. Mark completion only when the requested Prep work and cleanup are complete. For standalone Prep, offer `PHDK uat` as an optional future command or identify the single genuine blocking prerequisite; do not execute acceptance. For Prep within an active explicitly initiated UAT run, continue eligible acceptance cases under that authorization. Auto does not run Prep or UAT.
