# PHDK Auto Retrospective and Improvement Proposals

## Reusable implementation findings (v2.89.0)

A completed donor milestone can note candidates for `PHDK export modules` in its existing local retrospective when evidence suggests generalizable capability. This is a **suggestion**, not permission to run the inventory, publish private implementation, create a canonical issue/PR, or delay delivery. Only an explicit later owner-invoked Export Modules workflow can inventory that current authorized donor and request selected upstream contributions under `PHDK_EXPORT_MODULES.md` and `PHDK_REUSE_CATALOG_STANDARD.md`. Avoid duplicate telemetry, extra agents and recurring scans.

## Purpose and authority

Every Auto/Auto Force run performs one bounded learning closeout under the current project mandate. Learn from observed delivery, not from speculative dissatisfaction with safeguards. This standard creates proposals, not permission to change PHDK, another repository, a provider, spending, UAT scope or host controls. `EXECUTION_SCOPE.md`, `PHDK_AUTO.md`, `PHDK_AUTO_CONTINUITY.md` and the actual current owner request remain authoritative.

## Timing without a new delivery gate

1. During the run, retain only material observations in existing task/evidence records; do not create an extra journal or interrupt implementation to review the framework repeatedly.
2. During final Check/delivery preparation, review those observations once against the adopted PHDK version/ref, actual applicable rule and current project constraints. Draft the retrospective in the same final authorized change, before its normal version/PR delivery. Do not hold completed earlier milestones for it.
3. After the final publication attempt, report what actually shipped, the observed PR/main/version and deployment/acceptance states, then summarize the learning. Store final merge evidence in the existing post-merge delivery artifact; never invent the future merge SHA in a committed report or create a recursive report-only release to record its own SHA.
4. On a real terminal blocker, record a partial retrospective using available evidence after exhausting permitted repairs and independent work. Do not claim Auto finished. An owner stop/cancellation does not authorize extra writes; give only the permitted handoff.

The learning activity is mandatory, but approval or implementation of its proposals is not a development, acceptance or cutover gate. Do not reopen a delivered milestone for missing retrospective persistence. Report `RETROSPECTIVE_RECORDED`, `NO_GENERALIZABLE_FINDINGS`, or `RETROSPECTIVE_PARTIAL` honestly and preserve the actual delivery result. A temporary tool/storage failure must not be disguised as a successful report.

## Artifact and minimal content

Use `docs/decisions/phdk-process-review.vN.md` with stable `doc_id`, document version, dates, status and truthful `authority` under `PHDK_DOCUMENTATION_STANDARD.md`. Reuse an existing compatible review rather than creating a parallel document. Link it from `docs/INDEX.md`, the current task and the existing `90-delivery/HANDOFF.md` / `DELIVERY_REPORT.md` where applicable. A draft proposal is not an approved policy, even when its report is published.

Record the run/goal, adopted PHDK version and ref, inspected source/evidence references, actual outcomes and limitations. Each material finding includes:

- Stable finding ID; observed problem and evidence; exact rule/path and baseline; impact, with unexposed time/token/cost measurements marked `UNKNOWN`.
- Cause classification: `PHDK_GAP`, `PROJECT_SPECIFIC`, `HOST_OR_PROVIDER_LIMIT`, `MISINTERPRETATION`, or `EXISTING_SAFEGUARD`. Explain why a real safeguard is or is not proportionate; a refusal alone does not prove a framework defect.
- Smallest proposed change; applicability trigger across projects; safeguards to preserve; affected standards/entrypoints; proposed verification including a negative scenario and adoption/compatibility impact.
- Disposition: `PROPOSE_CANONICAL`, `APPLY_LOCALLY_IF_AUTHORIZED`, `ALREADY_SUPPORTED`, `REJECT_WITH_REASON`, or `NEEDS_EVIDENCE`; next owner/action, without implying that the action was authorized or performed.

Prefer a small number of substantive findings; zero is valid. Do not manufacture recommendations to fill a quota, repeat an unchanged prior proposal, or claim savings without comparable measured evidence. Link an existing finding/issue when known instead of duplicating it. Read only the relevant standards and evidence; a full canonical audit, extra agents or model upgrades are not required.

## Generalization and safe feedback

A canonical candidate must express a reusable problem and a conditional capability/contract that makes sense across repositories. Keep client names, proprietary schemas, real financial records, credentials, personal data, private implementation details, host-specific worker limits and subscription/model assumptions out of a public proposal. A private source link can also disclose information: do not publish it without current authorization. Use a minimal synthetic example when needed.

Do not copy every local restriction into PHDK. Separate actual owner intent, agent interpretation, tool capability and external enforcement. Prefer clarifying scope and evidence to removing a protection merely to avoid a stop. Never propose bypassing real host/security controls, fabricating acceptance, automatic production data migration or unattended work as a productivity improvement.

A downstream Auto run writes its review only inside its authorized project. It does not automatically open an issue/PR, submit telemetry, edit canonical PHDK, upgrade other projects or trigger another agent. A separately scoped current owner instruction can authorize canonical contribution through `PHDK_EVOLUTION_STANDARD.md`; do not demand duplicate approval for that same identified contribution once genuinely granted.

## Canonical response and return handoff

When the owner requests incorporation, the PHDK maintainer evaluates each finding against fresh canonical main. Return a finding-by-finding record: adopted and generalized, already covered, local-only, deferred, or rejected with reasons. Include exact changed standards, resulting version/PR/main evidence, checks actually run and remaining limitations. Do not claim publication for a draft PR or downstream adoption for a canonical merge.

Give the originating project a ready-to-use handoff explaining what to synchronize, what remains project-local, which evidence/decisions must be supplied, and which operations remain unauthorized. Synchronization follows `PHDK_UPGRADE.md`, preserves owner customizations and never converts an advisory report into a permission token.

## Owner-facing closure

After truthful delivery reporting, say what was learned and which PHDK improvements are proposed, linking the report. Separate proposals from implemented changes and general improvements from project-local actions. Finish the current request; no background monitoring, recurring reviews, automatic canonical maintenance or new approval ceremony follows from this closeout.
