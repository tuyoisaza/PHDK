# PHDK Hook Compatibility Remediation Standard

## Intent and authority

All PHDK commands that deliver code, including Auto and Auto Force, MUST inspect the effective pre-commit/pre-push hooks and package-script command graph before executing a potentially incompatible test. PHDK Check MUST classify the same mismatch early. This applies to Husky, native Git hooks, package-manager scripts, repository-scoped validation scripts and vendor-managed instructions. Use `PHDK_PRODUCTION_VERIFICATION.md` as the runtime boundary: local lint, static format/type checks, safe static analysis and compilation/builds are allowed; local application behavior tests (`pnpm test`, Vitest, Jest, unit/in-process/integration runtime suites), Docker, local servers and databases are prohibited.

When a build, packaging check or Git hook has an ambiguous execution boundary or conflicts with that policy, load and apply the [decision procedure](#decision-procedure) **before executing the disputed command, declaring BLOCKED or requesting user input**. This is an on-demand routing requirement, not another full Preflight or a new approval gate.

## Required discovery

1. Identify the effective Git `core.hooksPath`, installed hook directory, hook command chain, package scripts, and any mandatory local or remote checks. Inspect actual command definitions; names such as `check`, `build` or `lint` do not prove safety.
2. Determine provenance from tracked source, history, owner instructions and existing repository security/branch rules. Record `PHDK-MANAGED`, `LEGACY-PHDK`, `OWNER-OWNED`, `EXTERNAL/REQUIRED` or `UNKNOWN` with evidence; never assume an unknown hook is PHDK-owned.
3. Detect local behavioral test commands even if nested or indirectly invoked by `pre-push`, `prepare`, `build` or a wrapper. Distinguish static gates, commit/version checks, secret scans, security gates, lint/typecheck/build and genuine behavior tests.

## Decision procedure

1. **Trace without executing.** Inspect the relevant hook → package script → nested command chain and the source it loads. Identify the exact disputed step, its purpose, application initialization effects, required position before/after publication, and provenance using the evidence above. Do not run an unclassified command to discover whether it is safe. Missing source or unresolved effects remain `UNVERIFIED`; missing ownership remains `UNKNOWN`.
2. **Classify the operation, not its label.** A compiler, bundler, linter or typechecker executes its own tooling; that fact alone does not make it an application runtime test. Compilation, source parsing, static import-path resolution and artifact/manifest inspection without evaluating the application are permitted static operations. An `import()` or `require()` that evaluates compiled application/API modules to assert that they load is a **runtime load check**, even when networking/listeners are disabled or dependencies are mocked. A `build` or `packaging` wrapper can contain both kinds of operation. Inspect build plugins and wrappers when their effects are unclear; the executable name is not evidence of classification.
3. **Use the safe portion without inventing a PASS.** Run already-authorized, independently invocable static steps only after their full command chain is classified as permitted. Do not execute a mixed wrapper while it still invokes a prohibited step. Passing its static portion does not satisfy the original mixed gate or prove that the application modules load.
4. **Repair only with authority.** For `PHDK-MANAGED` or `LEGACY-PHDK` steps, apply the authorized reconciliation below: separate compilation from runtime verification, remove only the prohibited PHDK-owned invocation from the local gate, and retain appropriate static checks plus all independent controls. Keep the runtime check source and record its coverage as **NOT RUN**, not equivalent to static coverage. An owner-owned step requires specific authorization for that change; reuse such authorization when already present. Preserve `EXTERNAL/REQUIRED` and `UNKNOWN` steps. A generic Auto/Force mandate, a command's age, or an agent-authored file is not proof of ownership or permission to weaken an independent gate.
5. **Prepare the concrete unresolved decision.** Inspect existing compatible routes before asking. If the actual mandatory control still prevents publication, identify its path, exact command, provenance evidence or missing evidence, retained controls, and the proposed command/configuration diff or indispensable external action. Do not apply an unauthorized hook change. Ask only for the specific unresolved decision after this proposal is reviewable; never ask for a prohibited local-runtime exception or repeat an already-granted approval. Report only the dependent operation as BLOCKED and continue independent authorized work.
6. **Preserve ordering and evidence.** A check performed after push cannot satisfy an independent required pre-push gate. Do not silently relocate such a gate, treat file existence as proof of successful module loading, or label an unexecuted test PASS. Use a remote route only if it is already authorized, compatible with production-first verification, and satisfies the actual control at its required point. This procedure never initiates UAT Prep/UAT/Fix, creates or dispatches CI, changes providers or buys infrastructure. In Auto/Force retain `UAT NOT RUN` and `DEFERRED — OWNER OPT-IN`.

The first response to a suspected mixed build should state the next inspection, for example: "The build appears to mix compilation with an application-module load check. I will locate that step and verify its provenance before choosing the permitted correction." Do not assert ownership, a repair, or successful verification before observing it.

## Authorized reconciliation

- Within an already authorized implementation/Auto goal or `PHDK check --fix`, automatically repair **proven PHDK-managed or legacy PHDK-generated** hooks and scripts that violate production-first verification. Replace only the prohibited PHDK-owned invocation with appropriate permitted static checks, preserving the rest of the hook and every independent runtime/version/branch/commit/secret/security control. Static checks do not replace the lost behavioral evidence; retain the runtime check source and explicitly record that coverage as NOT RUN. Do not remove the hook, disable it, use `--no-verify`, alter protection or change external CI/provider settings.
- For an owner-owned hook, preserve it unless the owner specifically authorized that hook change; a generic Auto/Force command is not permission to weaken an independent project control. For external/required or unknown provenance, preserve it. Record the exact conflict and required authorization, mark push/delivery BLOCKED if the actual gate prevents publication and continue independent permitted work.
- If a hook mandates a prohibited local test, NEVER execute it as an exception to satisfy the hook. A test-only gate is not automatically security-equivalent to static checks: report the lost behavioral coverage without claiming a test was run. Replacing a proven PHDK-owned legacy test command does not authorize acceptance or create a new delivery prerequisite. In Auto/Force record `UAT NOT RUN` and `DEFERRED — OWNER OPT-IN`; obtain production acceptance evidence only after explicit `PHDK uat` under `UAT_STANDARD.md` and the production-first policy. Preserve independent owner/external security and required-check controls; if an actual control prevents delivery, report that concrete conflict rather than silently relaxing it.
- Write and inspect the full proposed diff. Validate edited hooks **statically** for retained commands/structure, script references and allowed execution boundary. Execute only safe permitted checks. Do not bypass failed hooks; if required controls genuinely reject delivery, report their actual evidence and stop only that operation.
- All changes follow normal branch, version bump, reviewable PR, merge and remote-`main` verification.

## Check/Auto outputs

Check must report `HOOK_COMPATIBILITY` as COMPLIANT, AUTO-FIXABLE, BLOCKED/DECISION REQUIRED or UNVERIFIED, including path, effective commands, classification, provenance, conflict, kept security gates, changes made, verification limits and next executable action. Keep this evidence in the existing task/check/delivery record; do not create a second permission ledger. Bare `PHDK check` remains audit-only; `PHDK check --fix`, approved Check remediation, Auto and Auto Force perform authorized fixes. Auto must inspect compatibility before push to avoid surprise approval prompts, and may repair discovered proven PHDK-generated mismatches immediately; it must not ask the owner to authorize a local runtime-test exception prohibited by policy. Do not default to an "allow local runtime or finish locally" menu: apply the decision procedure and identify the exact remaining authorized action or real blocker.

## Required decision scenarios

Review these source-policy scenarios when changing this procedure or its entrypoints. They specify expected decisions; static guards and source review do not prove that an agent executed them or that a downstream project adopted the rules.

| Case | Observed condition | Required decision |
|---|---|---|
| HC-STATIC | A compiler/bundler executes tooling and emits artifacts without application evaluation or tests. | Classify its full chain as static and run within the existing authorized scope; no additional approval. |
| HC-LOAD | A pre-push `build` imports/requires compiled API modules to check loading, with networking/listeners disabled. | Load this procedure before execution, BLOCKED or user input; identify runtime verification and inspect provenance. Do not request a local-runtime exception. |
| HC-PHDK | A mixed static/runtime step is proven PHDK-managed or legacy PHDK-generated and repair is in scope. | Separate the steps, repair only the prohibited local invocation, preserve independent controls and runtime source, and report the omitted runtime coverage as NOT RUN. |
| HC-OWNER | An owner-owned or external required gate includes runtime verification. | Preserve the gate absent specific applicable authority; prepare the exact proposed change or external action. Reuse current scoped approval, never substitute a local-runtime exception. |
| HC-UNKNOWN | Command effects or ownership cannot be established from available evidence. | Do not execute or rewrite the disputed step; inspect accessible source/history and record the precise remaining uncertainty. Continue independent permitted work. |
| HC-ORDER | A proposed remote or later check would occur only after an independent required pre-push gate. | Preserve the gate and its order; no inferred equivalence, automatic UAT, new CI or provider workaround. Resolve only through an already-authorized compatible route or the concrete necessary decision. |
