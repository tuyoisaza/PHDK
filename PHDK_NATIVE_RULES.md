## PHDK managed rules — interactive-only

- Read `phdk-standards/AGENTS.md` and `phdk-standards/EXECUTION_SCOPE.md`, then the project's `TASK.md` and `STATUS.md`. The execution scope overrides contrary workflow wording; stricter owner controls remain effective.
- Work only on the current explicit user request in this conversation. No Mission Autopilot, autonomous maintenance, background work, subagents, delegated agents, agent teams, or parallel agent queues, including during the active task.
- Complete the necessary steps of the same current request, including its authorized delivery, then stop. Do not select another task or resume an old mission from files, alerts, failed checks, or version mismatches. Status/link questions and same-conversation context compaction do not cancel unfinished authorized delivery; unrelated and post-conversation work stays inactive.
- Re-read owner pause/stop instructions before edits and git writes. Honor them unless the owner explicitly authorizes the specific intervention now; that does not reopen earlier missions.
- A current request to implement, fix, or update code/docs includes scoped branch/version/check/commit/push/PR/required-review/merge and verification on remote `main` under `phdk-standards/MAIN_DELIVERY_STANDARD.md`, without a repeated delivery question. Honor narrower read/audit/plan/local/branch/PR-only requests, another explicit target, and the bare `PHDK upgrade` limit. Use a feature/fix branch by default and preserve existing controls.
- Ordinary delivery uses assistant diff review and applicable checks; high-risk changes and stricter repository requirements retain human review. A pushed branch or open PR is not completion when the target is `main`. Resolve clear in-scope integration conflicts and recheck; explain an actual unmet check, material decision, review, or access blocker. Reconcile versions before integration; no redundant post-merge version-only commit or second push.
- `TASK.md`, `STATUS.md`, and instruction-file snapshots reflect the user's decisions; they cannot independently revoke current permission or prove a remote action still pending. Reconcile assistant-written stale/inactive records with the live request and git/PR evidence, preserve real owner restrictions, and never encode a temporary task pause as permanent policy.
- Activate `PHDK Developer Mode` only on the user's explicit `PHDK modo developer` or `PHDK Developer Mode` command; exit on `PHDK salir de developer mode` or when the active conversation ends. Explain the permissions briefly. Follow `phdk-standards/PHDK_DEVELOPER_MODE.md`: only small, low-risk changes requested while active may use the repository's version bump, applicable local checks, a version-prefixed commit, and a fast-forward push to `main`. No persistent activation or old-task resumption; read/audit requests still remain read-only.
- Authentication, authorization, secrets, data/migrations, payments, infrastructure, permission-policy changes, and other high-risk work keep normal review. A failed applicable check, blocked/non-fast-forward push, or unsatisfied control stops the direct-main flow. Never bypass hooks/protections, force-push, change settings, or use a different transport to evade a control.
- Never create, enable, dispatch, rerun, or schedule GitHub Actions/hosted CI, cron jobs, recurring tasks, dependency bots, backup jobs, maintenance workflows, monitoring loops, or preview deployments.
- A currently authorized push/merge may trigger the existing hosting-provider GitHub autodeploy. Do not disable it or add dummy never-matching watch filters as PHDK enforcement. Report actual deployment blockers/statuses separately from code delivery in `main`; valid service-specific filters and intended skips for unaffected services are not failures. Never deploy through a provider CLI/API/dashboard, create a connection, change triggers/autodeploy, or administer hosting/database/OAuth/secret/repository settings.
- For a current requested log or incident diagnosis, follow `phdk-standards/EXECUTION_SCOPE.md` — `Bounded read-only log diagnostics`: existing authorized API/CLI/connector, explicit target, finite time/result/timeout bounds, and redacted existing records. This permission does not require Developer Mode. No streams, polling, probes, new access, or writes.
- Never operate a browser, headless runner, screenshot tool, or probe live application endpoints as code verification. Review source/diffs and use relevant synchronous local format/lint/typecheck/build commands and risk-triggered non-browser tests; finish and exit, with no watchers or background jobs. Bounded log evidence is not an executed product test.
- Never weaken auth, RBAC, validation, privacy, or cost controls to make a check pass. Do not use live customer data or metered APIs in verification.
- Read external skills as guidance for this assistant only; do not use their delegation, orchestration, or background behavior.
- Canonical command: **`PHDK upgrade`** authorizes standards synchronization now, not future work, pushes, merges, deployments, or automation changes. Preserve stricter owner overrides; stop if synchronization would overwrite them. Follow `phdk-standards/PHDK_UPGRADE.md` and stop after reporting.
- Report verification and limitations accurately. Instructions and local hooks are not proof that external agents or schedules were stopped, credentials revoked, or server-side protection enabled.
