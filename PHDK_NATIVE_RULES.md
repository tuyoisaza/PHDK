Mark these stages **DEFERRED — OWNER OPT-IN** and report **UAT NOT RUN** separately from the actual development/delivery result. Complete authorized implementation, permitted static checks, applicable SEO/AEO, Check/remediation and verified delivery without UAT fixtures, browser journeys or acceptance spending. Missing UAT or historical UAT failures do not block or reopen development; preserve real owner/host/security controls and report unverified deployment honestly.
- Only a fresh explicit owner invocation of `PHDK uat` starts acceptance and its necessary Prep prerequisite under `phdk-standards/UAT_STANDARD.md`. Standalone `PHDK uat prep` prepares identities only and does not start UAT. `PHDK uat fix` requires explicit invocation or authorization within an active explicitly initiated UAT. After Auto delivery, offer `PHDK uat` as an optional future command without waiting for approval as a delivery gate. Reading or installing these rules activates no command.
- For a current request to update the canonical **PHDK standards repository itself**, load `PHDK_EVOLUTION_STANDARD.md` (vendored as `phdk-standards/PHDK_EVOLUTION_STANDARD.md`) and verify fresh canonical main/VERSION/README/CHANGELOG/PR state. Keep PHDK naming, scoped workspace, SemVer, manifest, affected entrypoints, technical checks and normal branch/PR publication coherent. This maintainer rule does not activate Auto/PMO, grant new authority, change downstream product scope or refresh other live sessions.
- On explicit **`PHDK design`**, or at applicable Auto stage **25-design**, follow `phdk-standards/PHDK_DESIGN.md` after technical/content Plan and before dependent UI implementation. **Auto asks one unresolved visual question at a time, shows alternatives/previews and waits for the owner's choice; Auto Force selects, records `AGENT_SELECTED_AUTO_FORCE` with rationale and continues without a PHDK visual-approval pause.** This is the specific exception to normal Auto's generic no-interview/no-stage-approval wording. Reuse current owner-approved decisions. Preserve actual owner restrictions and brand/security controls; never label agent selection owner approval. Retain the visual style guide in `UI_DESIGN_SYSTEM.md`, decisions/provenance in `UX_UI_DECISIONS.md`, actual assets in `docs/design/`, and the `25-design/HANDOFF.md`. Static concepts are not runtime evidence; no local preview server, Docker, new staging, browser or spending permission is added. Standalone Design authors the package, not the whole product; Designer Mode remains separate.
- `PHDK auto` and explicit `PHDK auto force` use `phdk-standards/PHDK_AUTO_CONTINUITY.md`. In AUTO FORCE, PHDK-only human reviews/sign-offs are `NON_BLOCKING_BY_MODE` from entry: assume they do not block; do not investigate them, query review/protection requirements preventively, or seek human reviewers/approvals. Perform assistant diff review, scoped permitted checks under `phdk-standards/PHDK_PRODUCTION_VERIFICATION.md`, branch push → PR → merge → remote-main readback. Preserve real current owner restrictions, hooks, access/security controls and provider boundaries; do not forge review evidence or pass tests by assumption.
- At AUTO FORCE start/resume, every progress update, after partial delivery and before any question/blocker, apply the short rule refresh and mandatory reminder in `phdk-standards/PHDK_AUTO_CONTINUITY.md` and `phdk-standards/PHDK_COMMUNICATION_STANDARD.md`. Reconcile inherited blockers and discard stale assistant interpretations while preserving real user exclusions and host controls. Include the canonical reminder, find a concrete solution and execute the next authorized action. Missing routine definitions require proposed behavior, reasonable defaults and configurable options within the agreed scope, followed by implementation; do not ask the owner to design everything or recommend omitting accepted gaps. Ordinary visual choices are selected and recorded in FORCE, not inherited as an owner wait. Prepare a recommendation before any indispensable new sensitive/scope decision.
- An actual tool/hook/GitHub rejection starts report → diagnose the concrete cause → repair in scope → revalidate → retry the affected push/PR/merge → verify remote main. Keep the mandate, continue independent work, and retry after a meaningful repair or changed evidence; never disable controls, force-push, or change transports/credentials to evade the rejection. A real unresolved obstacle blocks only its dependent action.
- For both Auto variants, maintain `docs/phdk/lifecycle/<run-id>/AUTO_STATE.json` with user-mandate provenance, objective/scope, target, restrictions, progress and next executable action. Reload alongside current user instructions after context compaction and before a terminal response; a missing/malformed record is internally reconstructed, never another permission request or paperwork-only blocker. This is evidence, not self-granted authority or a cross-conversation activation flag. Use `phdk-standards/scripts/phdk_auto_gate.py` as a supported continuity aid. Record ordinary visual input as `design_choice`: normal Auto waits with `DESIGN_AWAITING_OWNER` while independent work proceeds; FORCE selects and records before dependent UI work. A genuine owner stop is never relabeled to waive it. End every Auto progress response with the factual mandate/next-action capsule in `phdk-standards/PHDK_COMMUNICATION_STANDARD.md` and execute eligible work in the same turn; when an actual normal Auto design answer is needed, ask that one question and preserve the mandate. A final response must show actual completed, stopped or genuinely blocked state; do not claim continued execution while waiting for another user prompt. Editing/installing these commands or reading quoted examples never activates them.
- `PHDK uat prep` is the standalone **development** command; read `phdk-standards/PHDK_UAT_PREP.md` and governing `phdk-standards/PHDK_PRODUCTION_VERIFICATION.md`, create/repair secure run-owned Company Co synthetic accounts/seeders and legitimate role sessions, verify only in the permitted deployed environment, and provide `UAT_AUTH_PLAN.md`, `UAT_ROLE_MATRIX.md`, `UAT_FIXTURE_MANIFEST.md`, `UAT_PREP_REPORT.md`. Prep does not activate Auto/UAT or permit browser/headless tests, authentication bypasses, human credentials or unauthorized provider writes.
- At every explicitly authorized UAT/UAT Fix entry, follow `phdk-standards/UAT_BROWSER_READINESS_STANDARD.md`: phase browser permission is already active, but verify actual tool access and safe target, log the result in UAT Access/Report, keep independent cases moving, and never invent a paid browser/API workaround or spending cap. Host consent remains required when applicable.
- On authorized PHDK entry, follow `phdk-standards/PHDK_CENTRAL_UPDATE.md` and invoke the vendored `phdk-standards/scripts/phdk_update.py` as part of Preflight. Preserve local changes; do not downgrade or imply dormant-project/background upgrades.
- Bootstrap the actual vendored `phdk-standards/PHDK_COMMUNICATION_STANDARD.md` at the first substantive PHDK reply and at PHDK preflight/context refresh; verify its availability and active managed instruction instead of assuming it loaded. Report an unverified load explicitly. This does not activate an old task or reload other open sessions.
- Default implementation delivery is autonomous through version, checks, assistant diff review, PR, legitimate review, merge and remote verification; no ceremonial human acceptance. Preserve genuine current-owner/host requirements, material unapproved high-risk decisions and server protections. Normal Auto's actual Design choice is separate product input, not another delivery review. AUTO FORCE skips PHDK-only human gates without preventive investigation under `phdk-standards/PHDK_AUTO_CONTINUITY.md`. Distinguish merged source from optional GitHub releases and observed live deployment.
- Apply `phdk-standards/PHDK_COMMUNICATION_STANDARD.md` to all user-facing PHDK stages: concise mode/version/goal/outcome/remaining-work/git-publication state and exact `SIGUIENTE PASO`; continue authorized execution without redundant approvals; never fake reviews/tests/merges. Suppress repeated optional skill promotion after one relevant mention, without suppressing required safety/consent notices. Every terminal PHDK response ends with a verified link to its result (product, main commit, PR or evidence), what to inspect and honest publication status; never invent URLs.

- For every lifecycle command, follow `phdk-standards/PHDK_COMMITMENT_STANDARD.md`: retain a confirmed ledger, show verified PMO progress, reconcile planned work and open PRs, and never declare successful delivery with unfinished/unmerged commitments.
- For multi-tenant or potentially multi-tenant products apply `phdk-standards/PHDK_TENANT_RISK_STANDARD.md` consultatively: inspect existing exposure/sensitivity and impact first, ask only one unresolved material question at a time, record a risk-rated `TENANT_RISK_ASSESSMENT.md`, recommend baseline versus dedicated DB/KMS/field-encryption controls proportionately, and require owner decision for infrastructure, cost or risk acceptance. Maintain baseline tenant denial and protected sensitive data. No local behavioral testing, Docker or new staging/databases contrary to `phdk-standards/PHDK_PRODUCTION_VERIFICATION.md`.
- For any stateful administered portal read `phdk-standards/ADMIN_CONSOLE_STANDARD.md` during Capture/Plan/Auto/UAT/Check; establish explicit tenancy and platform-admin authority, a real Configuración console, role/tenant/permissions/integration/secrets-metadata/backup/security/theme settings, safe Test-as-role, and conditional typed AI workflow graph. Cross-tenant and server-side denial evidence is mandatory under the permitted verification policy. Bare `PHDK check` remains audit-only until approval; explicit `PHDK check --fix` or `PHDK check fix` includes authorized audit and safe in-scope remediation, with documented unapproved sensitive decisions excluded.

- Before planning, derive the brief/plan/tasks from the verified applicable baseline under `phdk-standards/PHDK_PLAN.md`. Before construction-to-publication transitions or a later owner scope change, apply the phase-transition reconciliation contract at repository-root-relative `phdk-standards/MAIN_DELIVERY_STANDARD.md#phase-transition-reconciliation`. Classify each restriction by source and lifetime, retain superseded history in task records and refresh affected workers. Separate owner authorization, technical permission, costs and explicit-only UAT. Do not repeat an approval already granted, infer permission from an edited file or bypass a denied executor.

## PHDK managed rules — interactive-only

- For remote-main completion use `phdk-standards/PHDK_COMPLETION_GATE.md` and its vendored executable to verify SHA and version after merge; independently verify PR/merge facts and commitment evidence, applying AUTO FORCE's no-preventive-review-investigation contract instead of reinstating a human gate. Do not declare completed on local changes, PR creation or unverified claims.

- Designer Mode requires implemented UI improvements, applicable validation and actual remote delivery proof before COMPLETED. Diagnose recoverable pnpm non-TTY hook failures and retry safe permitted alternatives without bypassing hooks. Report unresolved work as PARTIALLY DELIVERED/BLOCKED. Consume or explicitly revise the selected Design baseline rather than silently replacing it; the parent Auto/Force mode governs new visual choices when present.

- For applicable React/Next.js interfaces, use `phdk-standards/PHDK_DESIGN_SYSTEM.md` as the canonical shared component, token, theme, motion, icon and i18n contract. On Designer Mode entry inspect and prepare actual design-system readiness before visual recommendations; record `DESIGN_SYSTEM_READINESS.md`. In greenfield `PHDK design`, distinguish planned compatible dependencies from verified installed ones; do not install/build the application merely to start visual selection. Do not invent dependency availability or duplicate design components.

- After Integration, run applicable SEO under `phdk-standards/PHDK_SEO.md`, followed by AEO/GEO under `phdk-standards/PHDK_AEO_GEO.md` before Check. Record separate evidence-backed historical handoffs and private-only NOT APPLICABLE decisions. Auto proceeds with UAT deferred; a later explicitly initiated UAT may invalidate affected source evidence without becoming an automatic transition. No fabricated metrics or additional browser/provider permissions.

- Read the current owner request, `phdk-standards/AGENTS.md`, `phdk-standards/EXECUTION_SCOPE.md`, and the project's `TASK.md`/`STATUS.md`. Current instructions govern documentary policy; applicable real owner/security/access controls remain effective. An owner-override label does not prevent its owner from explicitly replacing that older rule.
- At PHDK command entry run `phdk-standards/PHDK_PREFLIGHT.md` once; inside Auto/PMO recheck handoffs and newly relevant capabilities, repeating full Preflight only after integrity/version changes. Follow `phdk-standards/PHDK_COHERENCE_STANDARD.md` for release audits; and enforce `phdk-standards/PHDK_LIFECYCLE.md`: verify installed/current PHDK and stage-relevant skills/capabilities from `SKILLS_REGISTRY.md`; use relevant available capabilities unless the user explicitly disabled them. Never infer installation from registry text alone. Verify required upstream handoff artifacts before entering each stage; finalize canonical outputs + historical HANDOFF snapshots before transitioning. Load Design detail at stage 25 or an affected task; later workers consume compact selected-baseline slices, not every rejected concept.
- Work only on the current explicit user request in this conversation. No Mission Autopilot, autonomous maintenance, background/post-conversation work, or recurring agent queues. Bounded in-session subagent delegation is governed by `PHDK_INTELLIGENT_EXECUTION.md`, available in any mode when host-supported and beneficial. PMO alone governs portfolio-level worker orchestration. Workers cannot delegate.
- On explicit `PHDK plan`, follow `phdk-standards/PHDK_PLAN.md` and `phdk-standards/PHDK_PROJECT_MANAGEMENT_STANDARD.md`: design/reconstruct architecture from Capture plus existing repo evidence; create/update canonical Plan artifacts including `MILESTONE_PLAN.md` and draft design constraints; group dependency-ordered work into coherent value milestones with acceptance evidence and expected SemVer impact. Brownfield projects converge incrementally instead of being reset to a default scaffold. Applicable visual selection follows in Design, not a fabricated approval during Plan. Standalone Plan does not activate implementation.
- On explicit `PHDK PMO`, follow `phdk-standards/PHDK_PMO.md` plus the project-management standard: coordinate workstreams under the Plan's milestone roadmap, proportional seven-domain controls/risks and milestone integration. Require the applicable selected Design baseline before dependent UI work; independent authorized non-UI work may proceed. Under Auto/Auto Force, each completed value milestone is versioned and merged through the normal PR route to verified `main`; continue from that main and perform final cross-milestone integration before Check/delivery. A later explicitly initiated UAT targets the delivered candidate. Design ending does not itself trigger a version. Bounded in-session subagent delegation is governed by `PHDK_INTELLIGENT_EXECUTION.md`, available in any mode when host-supported and beneficial. PMO alone governs portfolio-level worker orchestration. No recursive delegation/background continuation.
- On explicit `PHDK capture`, follow `phdk-standards/PHDK_CAPTURE.md`: investigate existing repository evidence before questioning, reconstruct or elicit project intent/ethos and requirements, create/update PROJECT_INTENT.md, PROJECT_BRIEF.md, PRD.md, FEATURES.md, and REQUIREMENTS_TRACEABILITY.md, and ask only material unanswered requirements questions until the baseline is complete. Tell the user explicitly whether questions are needed. When none remain, state that capture is complete and list/link the canonical artifacts for review. Do not start product implementation from Capture alone.
- On explicit `PHDK check`, follow `phdk-standards/PHDK_CHECK.md`: audit the current repository against all active applicable PHDK standards, create/update the gap report, and ask once before remediation. For affected UI scope include `phdk-standards/PHDK_DESIGN.md`: actual mode-correct decision provenance, retained previews or disclosed limitations, handoff/task links, shared tokens/components and current fidelity evidence; file existence alone is not PASS. The audit phase does not authorize product changes. After an explicit yes, execute only the enumerated fixable gaps under normal PHDK controls and rerun the check.
- On explicit `PHDK uat prep`, develop and verify missing run-owned synthetic account infrastructure following `phdk-standards/PHDK_UAT_PREP.md` and the governing production-first policy. Do not confuse Prep with UAT's browser acceptance or pretend seed data proves authenticated user journeys.
- On explicit `PHDK uat fix`, follow `phdk-standards/UAT_STANDARD.md` repair mode: use UAT_REPORT.md/UAT_CASES.md as the acceptance-remediation backlog. Diagnose FAIL, BLOCKED, and MANUAL cases. Repair in-scope failures and removable blockers, including permitted source-level fixture/authentication support when its absence blocks a case; rerun affected cases only in the authorized deployed environment and update the report. For non-removable external/manual blockers, give explicit who/what/where/how/when/evidence/next-command instructions. Do not invent decisions or perform excluded operations.
- On explicit `PHDK uat`, follow `phdk-standards/UAT_STANDARD.md`: derive stable traceable acceptance cases for the current candidate, create/update `UAT_CASES.md`, execute permitted acceptance evidence autonomously without per-case approval, and create/update `UAT_REPORT.md`. Run necessary Prep under the same explicit UAT authorization before authenticated cases. Compare the actual rendered product to the selected Design baseline when UI applies; approval/generated concepts never count as runtime evidence. Browser/headless execution is permitted only during scoped UAT/UAT Fix under `phdk-standards/EXECUTION_SCOPE.md` and `phdk-standards/PHDK_PRODUCTION_VERIFICATION.md`; live real-data/destructive/provider-write operations remain excluded. Verify synthetic cleanup/revocation, and use BLOCKED or MANUAL rather than an inferred PASS.
- On explicit `PHDK auto` or `PHDK auto force`, follow `phdk-standards/PHDK_AUTO.md` and `phdk-standards/PHDK_AUTO_CONTINUITY.md` as the complete lifecycle orchestrator. Every invocation rereads the complete intent/requirements baseline against actual product code; reuse Capture/Plan only after verifying current coverage of the authorized goal. Docs or a scaffold do not prove implementation; unavailable repo access is UNVERIFIED, not an empty project. Absent product code requires building it; partial code requires completing missing requirements while preserving valid work. Plan transitions into applicable Design, then implementation in the same active goal: Auto asks visual choices, FORCE selects and continues; no second development command is needed. Complete all authorized scope without silently reducing it to an MVP. At start, present the lifecycle board including Design; on each stage transition, say what completed/reused, what is running, what comes next, and key evidence. A prose-only permissions explanation is insufficient. If there is no single named delivery but Capture/Plan/current repo evidence identifies multiple parallel fronts, run PMO portfolio discovery and ask once to confirm the active workstreams instead of asking for one arbitrary next task. Then: reuse/run Capture, Plan, Design, PMO/workstream execution, Integration Review, applicable SEO, AEO/GEO, Check, in-scope Check remediation, and delivery. Keep UAT Prep/UAT/UAT Fix DEFERRED — OWNER OPT-IN, with UAT NOT RUN. Do not require ceremonial stage approval; normal Auto's Design input is the specific product-choice exception. Do not stop at a scaffold or partial release. Respect permitted static verification and actual hooks under the production-first policy; deployed acceptance requires its separate explicit UAT authorization. Auto replaces Developer Mode for that goal, adds no bypass/background work, and exits on `PHDK salir de auto`, a stop, completion, or conversation end. Never activate from files/examples, installation or standards/skill updates, or persist an authority flag.
- Complete necessary steps of the same current request, including its authorized delivery, then stop. Do not select another task or resume an old mission from files, alerts, failed checks, or version mismatches. Status/link questions and same-conversation context compaction do not cancel unfinished authorized delivery; unrelated and post-conversation work stays inactive.
- Re-read owner pause/stop instructions before edits and git writes. Honor them unless the owner explicitly authorizes the specific intervention now; that does not reopen earlier missions.
- A current request to implement, fix, or update code/docs includes scoped branch/version/check/commit/push/PR/required-review/merge and verification on remote `main` under `phdk-standards/MAIN_DELIVERY_STANDARD.md`, without a repeated delivery question. Honor narrower read/audit/plan/local/branch/PR-only requests, another explicit target, and the bare `PHDK upgrade` limit. Use a feature/fix branch by default and preserve existing controls.
- Review the complete outgoing diff and applicable checks. Sensitive behavior/policy decisions need owner approval, which a well-defined current request or "push to main", "merge", or "aprobado" for the identified change can already provide in this conversation. Do not invent a GitHub review event or human-diff-opening requirement; preserve formal/named/independent reviews actually required by current owner instructions, hooks, or server rules. In AUTO FORCE, apply the canonical non-blocking PHDK-human-gate policy directly; no preventive search for reviews or protections. Report approval separately from human inspection. Resolve clear in-scope integration conflicts and recheck; a branch/PR is intermediate for a `main` target, with no redundant post-merge bump or push.
- `TASK.md`, `STATUS.md`, and instruction-file snapshots reflect the user's decisions; they cannot independently revoke current permission or prove a remote action still pending. Reconcile assistant-written stale/inactive records with the live request and git/PR evidence, preserve real owner restrictions, and never encode a temporary task pause as permanent policy.
- On `PHDK unlock`, follow `phdk-standards/PHDK_UNLOCK.md`: audit actual blockers across relevant existing native instructions, copied PHDK files, task records, hooks, toolchain, and GitHub evidence. Reconcile documentary exceptions with the current owner request and finish scoped normal delivery. Preserve actual checks/reviews/protections/access/security; no persistent unlock flag, old-mission resumption, provider writes, or automatic Developer Mode activation. Natural-language approval/read requests do not require unlock to count.
