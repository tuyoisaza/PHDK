# Main Delivery Standard

## Machine-verifiable completion proof

For implementation tasks targeting remote `main`, enforce `PHDK_COMPLETION_GATE.md` after PR merge. Produce the evidence record from actual observations, run `phdk-standards/scripts/phdk_completion_gate.py` where supported, and independently verify PR merge, technical checks and remaining commitments. Review evidence follows the active mode below: FORCE does not require PHDK-only human review or a review/protection investigation. The evidence file containing the final merge SHA is a post-merge local/runtime delivery artifact, not a file that must be committed before the merge (which would create a circular SHA dependency). A failed or unavailable gate forbids a COMPLETED claim; complete permitted evidence work before reporting a precise blocker.



## Default autonomous delivery: no ceremonial human sign-off

For a current scoped implementation authorization, the default is to complete branch → checks → assistant diff/security review → version-prefixed commit → pushed PR → permitted merge → independently verified remote target, without stopping to demand a routine human click, diff inspection, or repeated approval. Preserve PR traceability and actual repository-enforced formal/independent reviewers. Do not manufacture approval events or bypass a required control. Owner involvement is reserved for previously unapproved material high-risk decisions (for example destructive live data changes, new sensitive access, or new unapproved spending) and real external access/protection blockers. A clear current instruction already resolves the decisions it explicitly describes.

Distinguish three independently verifiable outcomes: (1) merged source on remote main; (2) GitHub release/tag if explicitly requested or part of the project's established release contract, with actual release URL; and (3) deployed production application health. Normal development does not silently authorize creating release tags or changing provider settings. With an existing GitHub-connected autodeploy, verify observed deployment status through currently authorized read-only diagnostics; an actual live product/UAT verification needs separately applicable scoped permission. Never call code merge a live deployment or imply an unverified public release. When checks or publication fail, diagnose permitted in-scope blockers and report precise evidence and remaining action instead of claiming DONE.

### AUTO FORCE delivery

Under explicit `PHDK auto force`, follow `PHDK_AUTO_CONTINUITY.md`: PHDK-only human/manual/formal reviews, security signoffs and owner-diff-approval checkpoints are nonblocking by definition. Do not perform a preventive review/protection investigation, search for approvers or prove that a PHDK review is optional before attempting delivery. Perform the technical diff/security review, all mandatory permitted checks, scoped branch push, PR, merge to `main` and independent remote-result verification without another approval. Missing review events or inherited "awaiting review" labels do not block this flow.

Known actual controls and genuine current owner restrictions remain binding. An actual GitHub/hook/tool rejection starts the `PHDK_AUTO_CONTINUITY.md` repair-and-retry cycle: report briefly, investigate the observed cause, repair the in-scope technical/check/conflict/state defect, revalidate, retry the authorized branch push/PR/merge and independently verify `main`. Do not stop at the first rejection or ask for delivery permission again. Continue while a permitted repair or new evidence can produce progress; only then isolate an unresolved operation and finish independent work before requesting a concrete external action. Do not bypass hooks/protections, use an admin override, force-push, change settings/credentials, fabricate reviews or retry an unchanged rejected operation. FORCE authorizes the normal PR merge into `main`, not an unrestricted direct-main push or provider deployment. The mode-specific rule here takes precedence over generic PHDK review language in this document.

## Purpose and authority

Finish the user's current implementation request with the requested change integrated into remote `main`. `EXECUTION_SCOPE.md` governs authorization and exclusions; current owner instructions, existing hooks, review requirements, and access controls remain binding. This standard defines the normal branch/PR flow, independently of Developer Mode's narrow direct-main exception.

## The requested outcome includes delivery

A current request to implement, fix, or update repository code or documentation includes the necessary scoped branch, version bump, applicable local checks, version-prefixed commit, branch push, pull request, required review, merge, and verification on remote `main`. Do not require the user to repeat "merge and push to main" after the development work. Use another delivery target when the user or the repository explicitly specifies it; do not create or retarget a default branch merely to apply this standard.

Honor narrower requests such as inspect, audit, plan, edit locally, leave on a branch, or open a PR without merging. Their stated limit remains the deliverable. The exact `PHDK upgrade` command retains its synchronization-only contract unless the user also requests git delivery. No instruction here authorizes release tags, unrelated changes, a new task, or work after the active conversation ends.

An existing hosting connection may deploy automatically after the authorized update to `main`. PHDK's limits on autonomous coding, schedules, and Actions do not require disabling this GitHub-connected autodeploy or introducing dummy never-matching watch filters. Preserve valid service-specific watch paths. Report an observed disabled connection, a filter shown to exclude changes that need deployment, or an actual skipped/failed status for the relevant commit separately from code integration; an intended skip for an unaffected service is not a failure. Merge and deployment are separate facts; verify and report only the available evidence. Do not deploy or administer provider resources through a CLI/API/dashboard or change hosting/GitHub settings to finish delivery; a requested configuration intervention is a separate scope and cannot be inferred from a generic development request. A separately requested provider check uses `EXECUTION_SCOPE.md` — **Bounded read-only provider diagnostics** for relevant status, non-secret configuration metadata, and logs.

## Keep current authorization and task records consistent

- Preserve the authorization and target of the same unfinished request across turns in the active conversation. A status question, request for a link, clarification, context compaction, checkpoint, or assistant-written task summary does not cancel that request or remove its delivery steps.
- `TASK.md`, `STATUS.md`, summaries, and managed instruction files record the user's decisions; they do not independently grant, withdraw, expire, or narrow authorization. Do not mark an authorized unfinished delivery inactive merely because coding is finished or a newer message asks about progress.
- A real user stop, pause, cancellation, narrower target, or newer incompatible instruction takes precedence. Preserve its scope and provenance. An actual technical or review blocker pauses execution without pretending the user withdrew authorization. Never erase an owner's real restriction by relabeling it stale.
- When records conflict, compare the actual user instructions, their scope, and current git/PR evidence. Correct an assistant-generated bookkeeping error within the authorized task. Ask only if a material owner decision remains ambiguous; do not ask for a second grant already present in the active conversation.
- Never embed temporary task state such as "TASK remains paused" in permanent agent/routing instructions. Keep dated task facts in tracking records and verify them before relying on them. An unchecked commit/push/merge box is not proof that the remote operation is still pending.
- In a new conversation, do not resume an old task or restore Developer Mode from records alone. A new current request can explicitly resume the named work, including its stated delivery target. This continuity rule permits no background, scheduled, or post-conversation execution.
- For Auto/Force, maintain and recover the factual current mandate in `docs/phdk/lifecycle/<run-id>/AUTO_STATE.json` under `PHDK_AUTO_CONTINUITY.md`. A pending check, open PR, assistant-written status or context compaction does not withdraw the user's authorization. The record is evidence, not a standalone permission token; apply the continuity contract before any terminal BLOCKED report.

## Review according to risk and existing requirements

Review the complete outgoing diff and the changes needed for integration. Ordinary in-scope changes use the assistant's source/diff review and applicable local checks; PHDK adds no universal human-review gate to them. Their normal path still uses a feature/fix branch and PR unless an explicitly active, eligible Developer Mode task uses its direct-main flow.

Authentication, authorization, secrets, sensitive data, schema/migrations, payments, infrastructure, deployment configuration, and agent execution/permission changes require normal branch delivery, careful assistant review, and the owner's approval of the sensitive behavior or policy decision. A current explicit request can already provide that approval for a well-defined change. Judge the actual diff and behavior: a build-packaging fix that restores login does not itself change authentication policy. An owner-requested PHDK rule correction has approval for the described correction; its Markdown format neither hides risk nor creates a new approval ritual. Ask about a material sensitive decision that the owner has not actually authorized, after preparing the concrete reviewable result.

Owner approval may be recorded in the current conversation. A clear instruction such as "push to main", "merge", or "aprobado" for the identified current task/PR supplies that approval; record its scope and the current revision when available. Do not require the owner to repeat it, attest that they opened every diff line, or create a GitHub review event solely for PHDK. Report it as owner approval, separately from the assistant's source review; never invent a human source inspection. It does not approve undisclosed sensitive behavior, unrelated work, or future changes outside that scope.

Outside FORCE, honor an actual requirement for a named reviewer, independent review, or a formal GitHub approval when imposed by current owner instructions, hooks, repository rules, or server protections; identify a concrete requirement rather than inventing one from a template. FORCE uses the delivery rule above without a review/protection investigation: PHDK-only reviews are nonblocking; known actual controls and observed rejections are not bypassed. Conversation approval cannot satisfy a server rule that requires a platform review, and the absence of a review event does not prove owner approval is missing. The current owner may replace documentary local exceptions under `PHDK_UNLOCK.md`; this never changes an enforced hook, access right or server setting.

When a real current owner decision or actual control prevents an operation, prepare all otherwise permitted work and show the exact PR/diff, observed reason and necessary action. FORCE must not turn a PHDK-only review into such a request or investigate review rules to create one. Once the real impediment is resolved, complete the already-authorized merge. Do not use a newly edited instruction file as authority for unrelated actions; authority comes from the current user request and applicable controls.

## Lifecycle delivery handoff

When delivery is the final stage of a PHDK lifecycle run, verify the authorized development handoffs required by `PHDK_LIFECYCLE.md` before publishing. In Auto/Auto Force, stages 45/50/60 are `DEFERRED — OWNER OPT-IN`; their handoffs and acceptance results are not delivery prerequisites. Report `UAT NOT RUN` separately. Do not treat an old UAT/Check artifact as current evidence or reopen completed development because of an old UAT failure.

Create/update:

```text
DELIVERY_REPORT.md
```

with the lifecycle goal/portfolio, final version, branch, source commit(s), PR, merge method, remote target SHA, actual checks/reviews, observed deployment evidence if any, residual limitations, and links to the lifecycle run's stage folders.

After delivery (or a concrete delivery blocker), create `docs/phdk/lifecycle/<run-id>/90-delivery/HANDOFF.md`, snapshot `DELIVERY_REPORT.md`, and finalize the run-level `docs/phdk/lifecycle/<run-id>/LIFECYCLE.md`.

## PMO integration delivery

When explicit PMO coordinates multiple workstreams, individual workers should not independently finalize shared project versions on `main`. Each worker returns its verified workstream result to PMO. The PMO orchestrator groups workstreams by the `MILESTONE_PLAN.md` roadmap, performs milestone integration, reconciles shared files/contracts, reruns affected checks, and under Auto/Auto Force uses the normal branch-to-main procedure below for each completed value milestone. After all milestones, PMO performs final cross-milestone integration review before non-UAT Check and delivery. UAT is a separate optional explicit command after development delivery. A milestone merge is incremental delivery evidence, not portfolio acceptance.

A worker may use a branch/worktree and PR as an intermediate handoff when the repository/tooling benefits from it, but an open/merged worker PR is not by itself portfolio completion. Preserve actual repository protections/review rules.

## Normal branch-to-main procedure

For an explicitly active `PHDK auto` goal, use `PHDK_AUTO.md` for the full lifecycle. Capture/Plan define the roadmap; PMO/workstreams execute it; completed value milestones are incrementally delivered to `main`; permitted static checks and non-UAT Check/remediation establish development conformance. UAT Prep/UAT/Fix remain deferred until separately explicitly authorized, never an Auto completion prerequisite. Do not request human OKs or produce releases after each **stage**. Apply this procedure at each milestone delivery boundary and again only when later authorized development or explicitly authorized acceptance-remediation source changes require a new delivery. Treat the entire goal—not any single milestone—as final completion. An explicit Auto command switches that goal to this normal branch route from Developer Mode; repair real failures within scope while preserving every applicable control.

1. Identify the repository, remote, target, current task, owner instructions and local state. Inspect relevant hook commands, version scripts, package-manager requirements and technical gates early enough to resolve their prerequisites. Outside FORCE, establish applicable review requirements; FORCE does not query reviews/protection rules or search approvers and follows its delivery rule above. Preserve unrelated edits and other contributors' commits.
2. Start or continue the task's existing suitable feature/fix branch from a known target state. A new message or checkpoint does not require another branch for the same unfinished delivery. Keep the outgoing range limited to the approved task and necessary version metadata.
3. Implement the requested change. Run applicable synchronous local checks, with no browser tests, live probes, hosted CI dispatch, or provider writes. Auto/Force permit source/static/typecheck/safe-build checks under `PHDK_PRODUCTION_VERIFICATION.md`; test-source changes do not authorize local runtime suites or deployed acceptance. Inspect actual script effects and preserve current owner and security controls. A separately requested provider check uses the bounded read-only diagnostics in `EXECUTION_SCOPE.md`. Source/diff/reference checks suffice for ordinary documentation work unless the repository has a stricter applicable requirement.
4. If a check fails, keep publication blocked while diagnosing it. Repair a clear, bounded defect within the approved scope and rerun affected checks. A failing baseline does not authorize unrelated repository-wide cleanup, workflow behavior changes, unscoped dependencies, or weaker gates. Auto may make the necessary non-semantic formatting repairs defined in `PHDK_AUTO.md`, with equivalence evidence and no new approval ritual. If scope, review, toolchain, or access prevents resolution, isolate the blocked operation, finish independent permitted work, and report the specific blocker.
5. Refresh the remote target before final integration. Resolve routine same-task integration conflicts when the intended result is clear, retaining other contributors' work and the requested behavior. Use the repository's allowed method without force-pushes or history rewriting. Material ambiguity or a sensitive decision requires the appropriate review/decision, not an arbitrary choice of one side.
6. Reconcile the final version and changelog on the working branch against the current target and the repository's version standard. Review the integration result, rerun affected local checks, and apply the active mode's review rule. FORCE requires no PHDK-only formal review or review/protection lookup. Renew an owner decision only when the resulting behavior, risk, or scope goes beyond what was approved; an in-scope version/conflict reconciliation does not itself cancel the current task authorization.
7. Create the necessary scoped commit(s) with the resulting version at the start of each source-changing commit subject. Use existing hooks and required checks. Never disable a hook, ignore a failure, or choose an API/transport/credential to evade a control. If an applicable mandatory gate fails, preserve the publication gate while repairing within scope, revalidating and retrying; only an unresolved real limitation after permitted work prevents publication. A failed attempt does not terminate Auto/Force.
8. Push the working branch through the permitted path and open or update its PR. Apply the active mode's review rule: FORCE proceeds without PHDK-only reviews or approval searches and honors known controls and actual operation responses. Current scoped approval needs no repeated sign-off. A ban on direct pushes to `main` still permits the authorized PR route. Auto publishes the complete verified candidate, not an unverified intermediate stage.
9. Recheck the requested scope, target/head revisions and technical checks, then merge through the allowed method; outside FORCE, verify applicable required review evidence. FORCE does not perform a review/protection investigation before merging. Handle a new target change within this same bounded normal flow and revalidate the resulting change. An actual rejection enters the report/diagnose/repair/revalidate/retry cycle; do not stop automatically, blindly repeat a stale write, bypass a protection or pretend a rejected merge succeeded.
10. Verify the resulting commit/content and version on the remote target. Accommodate the repository's merge or squash method rather than assuming a feature-branch SHA must appear unchanged in `main`. Report the PR, resulting remote SHA/version, actual checks, and delivery state; then stop at the requested outcome.

## Version once for each required source change, not again for integration

Use the repository's actual version source, including `VERSION` where applicable. Account for existing bump hooks so they do not produce a duplicate bump. Additional source-changing commits follow the repository standard; do not promise a single version increment for an arbitrarily long task.

A merge or squash record that only integrates already-versioned changes does not require another version bump. Reconcile a version collision or changed source before integration, without reusing spent versions. Do not manufacture a post-merge version-only commit or empty commit to make a completed task look released.

A GitHub PR merge already updates remote `main`. After that operation, read back the resulting state; do not perform a redundant local merge and second push to `main`. When a repository explicitly permits local integration instead, only its required ordinary fast-forward push publishes that local result, with all controls intact.

## Completion and blocked delivery

For a request targeting `main`, local implementation, a versioned commit, a pushed feature branch, and an open PR are intermediate states. Mark the delivery complete only after verifying the requested change and consistent version on remote `main`.

When an operation remains blocked after permitted repairs and independent work, state the unfinished delivery step, exact observed check/conflict/rejection/access requirement or current owner restriction, what was actually committed or pushed, and the precise next action. Auto/Force must first apply `PHDK_AUTO_CONTINUITY.md`; FORCE does not investigate or block on PHDK-only reviews. Keep unfinished delivery in the same request; do not rewrite the user's permission as inactive or create a job to resume later.

Keep task records and final reporting honest. A record written before publication is a dated checkpoint; compare it with live git/PR evidence before claiming an operation remains pending or repeating it. Do not create a second release solely to stamp a post-merge checklist. A requested application URL should be an observed appropriate URL with the known delivery state; a local source-file link is not evidence of a deployed change. Missing deployment evidence is reported as such, without browser tests or provider writes.

## Developer Mode remains a separate direct-main flow

`PHDK_DEVELOPER_MODE.md` still requires explicit activation, an eligible small low-risk request, and the active conversation. Its failed-check, rejected/non-fast-forward push, and unmet-control conditions stop the direct flow immediately. The normal repair/integration steps above do not authorize automatic repair, rebase, merge, retry, or switching delivery paths to get around that stop. Report the blocker and wait for the user's next instruction.

## Mandatory delivery proof gate (fail closed)

Every implementation or standards change targeting `main` MUST pass the following machine-checkable evidence contract before the assistant reports COMPLETED. This applies to `PHDK auto`, PMO integration and normal delivery; no stage or PR creation substitutes for it.

1. **VERSION_BUMP=PASS** — read the canonical version from the target and candidate, apply the repository's semantic version policy, and prove the source-changing candidate has an appropriate fresh version (including other version-bearing files and the changelog when used). No duplicate bump for a merge-only record; never reuse a version already consumed on remote main. For concurrent merges, reconcile against refreshed remote main before finalizing.
2. **COMMIT_PREFIX=PASS** — inspect every new source-changing commit in the outgoing delivery range. Each subject MUST begin with the resulting version, e.g. `v2.49.1: enforce delivery gates` (accept `v2.49.1 ` followed by meaningful text where a repository uses that convention). Reject a missing, stale, or trailing-only version prefix. Merge/squash-generated records that only integrate already-versioned commits need no new bump, but give the integration commit a version-prefixed title whenever the permitted merge method allows it.
3. **PUSH_AND_PR=PASS** — confirm the branch exists on the remote and its PR targets the expected `main`. An open PR means IN PROGRESS, never COMPLETED. Complete the authorized merge through the normal permitted flow after technical checks and the active mode's actual controls are satisfied; FORCE does not require PHDK-only review or a review/protection investigation.
4. **REMOTE_MAIN=PASS** — after merging, re-fetch remote `main`, verify the expected version and changed content are present, and record the final remote SHA and merged PR URL/number. A local main branch, local commit, successful branch push, closed-unmerged PR, or successful merge request without readback is NOT sufficient.
5. **SCOPE_AND_CHECKS=PASS** — verify the original confirmed commitments, technical checks and applicable actual controls. In FORCE, PHDK-only reviews are `NON_BLOCKING_BY_MODE`, not an approval to collect; do not investigate reviews/protections for this proof. No in-scope open PR or unresolved confirmed item may be silently omitted. Report deployment status separately and do not infer deployment success from merge.

Record all five fields with PASS/BLOCKED, specific evidence, version, branch, PR and remote SHA in `DELIVERY_REPORT.md` and the lifecycle delivery handoff. If any field is not PASS, label the result **BLOCKED** or **PARTIALLY DELIVERED**, identify the exact failed operation and continue all other permitted work. Never describe the update as shipped, integrated, released or 100% complete until REMOTE_MAIN is verified. Do not ask the owner to reauthorize routine bump/commit/push/PR/merge already covered by the current goal. Do not bypass server rules, hooks or an actual independent review requirement to manufacture PASS.
